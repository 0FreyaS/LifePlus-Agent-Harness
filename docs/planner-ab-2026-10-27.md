# LifePlus 规划提速 A/B 测试结论

测试日期：2026-10-27。结论：**不启用候选 B，现用默认保持 A（`baseline`）**。

本次实现了可关闭的规划提示词压缩，以及 planner、intent、response 的独立模型配置入口。但实测未证明达到提速目标，并出现新增的缺参推断错误，因此没有修改真实 `.env` 或切换现用模型配置。实验实现与测试证据保留，不等同于已经发布优化。

## 1. A/B 分别测什么

| 条件 | A：baseline | B：compact |
|---|---|---|
| 真实模型 | 当前配置的 grok-4.3 | 同一个 grok-4.3 |
| 温度 | 0 | 0 |
| 业务规划规则 | 保留 | 相同 |
| 模型可见 Schema | 原始完整 Schema | 移除 title、description、default 元数据，并压紧 JSON 空白 |
| 输出上限 | 2048 | 独立 planner 配置 1536 |
| 运行时校验 | TaskPlan、PlannedTask、SlotValues | 完全相同的校验器 |
| 格式修复 | 最多额外一次 | 最多额外一次，计入时间和用量 |

空摘要时的系统提示词从 4485 字符缩至 3208 字符，下降约 28.47%。业务字段 `title` 不是 Schema 元数据，仍保留；枚举、依赖、字段类型和数值限制不删除。

这是“提示词压缩 + 规划输出配置”的组合实验，不是各因素独立的消融实验，也不是换小模型实验。职责拆分的接线由回归测试验证，不能由这次结果推导另一种模型的准确率或速度。

## 2. 固定数据与测量方式

- 30 个不同场景，六组各 5 个：单任务标点、独立并行、数据依赖、缺参、上下文引用、多任务上限。
- 每个场景重复两轮；每组版本各 60 次请求，总计 120 次请求。重复不是新的独立用户场景。
- 冻结参考时间为 `2026-10-27T10:00:00+08:00`。同一配对的 Query、摘要、时钟和标签相同。
- 随机打乱场景，交替安排 AB/BA；有效复测的配对并发为 1。同一配对内两个版本顺序执行。
- P50 使用中位数，P95 使用 nearest-rank；规划可用前的全部耗时均计入，包括解析、修复、超时和失败。
- 校验任务数、领域动作、标注槽位、不得推断字段、依赖边和结果绑定；容许不同任务 ID 与等价拓扑顺序。其他语义近似不会擅自改成通过。
- 不执行业务工具或真实写操作。本结果不是端到端任务完成率、首 token 时延、地图展示时延或系统生产 P95。

数据和评分器见 [planner_cases.py](../evaluations/planner_cases.py)，运行器见 [planner_ab.py](../evaluations/planner_ab.py)。

## 3. 最终有效复测结果

| 指标 | A | B | 解释 |
|---|---:|---:|---|
| 请求数 | 60 | 60 | 完整配对，无连接异常 |
| 规划契约严格通过 | 58/60（96.67%） | 57/60（95.00%） | B 新增一次缺失城市的错误推断 |
| 规划 P50 | 7.874 秒 | 7.734 秒 | 仅下降 1.78%，未达 15% 门槛 |
| 规划 P95 | 15.344 秒 | 15.888 秒 | 上升约 3.55%，没有尾延迟收益 |
| 实际模型调用 | 60 | 61 | B 有一次结构化修复 |
| input tokens 总量 | 103492 | 73244 | B 输入用量减少 |
| output tokens 总量 | 10452 | 10411 | 可见输出用量接近 |
| reasoning tokens 总量 | 33288 | 34439 | 输入变短并未同步减少推理用量 |
| total tokens 总量 | 147232 | 118094 | B 减少约 19.79%，不是货币账单降幅 |

该模型的回传用量中，`total_tokens` 包含单独报告的 reasoning 用量；cache read 是输入用量子项，不能再次加到总量。A/B 的 cache read 分别为 66816/39552，提供商缓存不可控。

按场景聚合两轮配对相对提速，再按场景 bootstrap 的 95% 区间为 **-8.64%～+3.03%**，跨过 0。该区间对应场景配对统计量，不是上述总体 P50 比值的区间，不能混用。

### 分组结果

| 场景组 | A 严格通过 | B 严格通过 |
|---|---:|---:|
| 单任务标点 | 8/10 | 8/10 |
| 独立并行 | 10/10 | 10/10 |
| 数据依赖 | 10/10 | 10/10 |
| 缺参 | 10/10 | 9/10 |
| 上下文引用 | 10/10 | 10/10 |
| 多任务上限 | 10/10 | 10/10 |

两组共有的失败是同一条健康知识问题在两轮中都路由为 `chat/chat_answer`，而冻结标签要求 `wellbeing/knowledge_search`。这是领域契约不匹配；未执行下游任务，不能直接解释为用户得到错误答案。

## 4. 为什么不切换：一个明确退化案例

配对 ID：`missing01:1`。

用户输入：

> 查明天天气，同时搜索周杰伦的歌曲

两组上下文均没有城市信息。

```json
{
  "A_weather_slots": {"forecast_date": "2026-10-28"},
  "B_weather_slots": {"city": "北京", "forecast_date": "2026-10-28"}
}
```

A 保持城市缺失，允许后续流程澄清或按有来源的业务配置处理。B 臆造北京，虽然参数类型通过 Schema，但语义来源错误，可能让下游跳过应有的城市补充流程。

这说明“结构化输出合法”和“槽位语义正确”是两层问题。单次观察不能证明具体由哪段元数据删除引起，但已经违反预先约定的“无新增配对错误”门槛；不能为了省 Token 忽略它，也没有根据这个失败反向修改本轮冻结标签或提示词。

另一个观察：B 在 `dependency02:1` 第一次输出未通过解析/校验，第二次修复成功，整条请求共 21.395 秒。两次调用和用量都已计入，不把修复后的成功当作一次快速调用。

## 5. 预设门槛与决策

| 门槛 | 结果 |
|---|---|
| 全部配对完成、无连接异常 | 通过 |
| B 严格通过率至少 95% | 通过，但样本小，不是生产准确率保证 |
| 总通过数不下降，且无新增配对失败 | **未通过** |
| P50 至少下降 15% | **未通过** |
| B 样本 P95 不超过 A 的 105% | 通过，但实际略慢 |
| 配对提速区间下界大于 0 | **未通过** |
| 用量完整且总 Token 不增加 | 通过 |

因此默认仍为 `PLANNER_VARIANT=baseline`，独立模型名称均未配置覆盖。本轮不以成本改善替代速度和质量验收，不启用未经单独评测的小模型。

## 6. 失败首测没有删除

首测使用配对并发 2，共记录 120 次请求；中途出现集中连接异常，A 有 49 次执行异常、B 有 48 次。大量快速连接失败让中位耗时落到毫秒级，**该数值不能作为提速证据**。

首测记录保留在本地 `data/benchmarks/planner-ab-20261027/live/`，有效低并发复测保留在 `live-serial/`。没有确认首测连接异常的完整根因，不把低并发重跑成功写成已经修复了生产并发连接问题。

两批都保存 manifest、冻结 cases、逐条 results、summary 和可读 report。首测不与有效复测混成一个通过率，也不从有效复测中再删除慢请求。

## 7. 回归、复算与边界

- 修改前：483 项通过、1 项跳过。
- 修改后：504 项通过、1 项跳过；新增 21 项，包含角色模型分发、子任务复用计划而不重复意图识别、Schema 约束保留、非法绑定、修复次数和“快速失败不得判提速”。
- 两批各 120 条结果均检查无重复键；冻结数据摘要一致；保留计划按当前同一验证器重算，评分与记录一致。
- 代码回归数量不是模型准确率。30 个手工设计场景不是随机生产流量，不能由此宣称 QPS、端到端 SLA 或全面上线安全性。
- 默认路径不启用压缩；实验实现保留在显式开关之后。真实 `.env`、工具 Key、底层模型名称及业务工具配置未修改。

在项目根目录复跑（会调用真实模型并产生用量，使用新目录）：

```bash
.venv/bin/python -m evaluations.planner_ab \
  --output data/benchmarks/planner-ab-new-run \
  --cases 30 --repeats 2 --concurrency 1

.venv/bin/python -m pytest -q
```

后续要验证专用快速规划模型或新的压缩方式，应作为新候选，使用独立验收集和同样的质量门槛，不覆盖本轮失败证据。
