# LifePlus 生产化策略：Query、信息时效与任务生命周期

更新日期：2026-10-24。

本文区分“本轮已加入代码并有回归证据”与“上线前仍需建设”。当前是本地运行的可交互项目，不能因为加入若干保护就宣称具备完整生产能力。

## 1. 总体原则

生产中的问题不仅是模型是否理解一句话，还包括：这句话要作用于哪次任务、引用的数据还是否有效、用户确认是否仍然适用，以及服务已经执行但响应丢失时能否安全恢复。

采用以下原则：

1. 先确定用户、任务、对象和时间，再执行。
2. 把历史记录、可用上下文和实时业务事实分开。
3. 有效期按数据类型制定，不用一个 Redis TTL 代表所有信息时效。
4. 过期首先撤销“可用于当前执行”的资格，不删除历史执行证据。
5. 读操作可以刷新；写操作不能因超时或重启而盲目重放。
6. 模型与工具输出都是需要验证的数据，不能获得宿主权限。

## 3. Query 策略：不是所有不清楚的请求都“拒答”

### 3.1 输入层与语义层分开

输入层处理空白、长度和格式问题，返回可解释的校验错误；语义层处理用户到底要做什么。

“附近找个饭店”是有价值的缺参请求，应问参考地点，不应因为信息不全而直接拒答。“第二个”必须有可用的候选上下文；没有绑定对象时，不能随意去最近一条 Trace 取序号。

### 3.2 生产场景矩阵

| 用户表达 | 应采取的策略 | 当前状态 |
|---|---|---|
| 空白、超长、含 NUL 控制字符 | 接入校验，不调用模型 | 已实现 |
| “无锡天气” | 结构化城市与日期，真实查询 | 已实现 |
| “附近有什么饭店” | 缺少参考点时澄清 | 已实现 |
| “东南大学”有多个真实候选 | 记录列表、候选选择 | 已实现 |
| “第二个” | 只在所绑定的有效中断中解析 | 已实现 |
| “第二个，同时查杭州天气” | 恢复原任务并创建新任务 | 显式连接词范围已实现 |
| “不要音乐，只查天气” | 识别否定范围，不新增音乐任务 | 依赖模型理解与场景回归，未保证通用覆盖 |
| “换一家，不要川菜” | 区分修改检索条件与选择候选，重新检索 | 通用约束修订协议待完善 |
| “算了，先别导航，查天气” | 明确取消对象与新任务，不把“算了”当目的地 | 复杂自然语言事件仲裁待完善 |
| “跟刚才一样”但刚才有多个任务 | 问要重复哪个任务，不凭最近时间猜测 | 需要进一步场景化设计 |
| “今天”跨过北京时间零点 | 不静默改变原日期，要求明确日期的新请求 | 恢复/刷新入口已拦截明显相对日期 |
| 长时间后选择旧列表 | 拦截过期输入，显式刷新并重新选择 | 已实现 |
| 用户提到工具不支持的预订/播放 | 解释能力边界，不生成虚假成功 | 有工具与回复约束；需文字级持续评测 |
| 检索内容要求“忽略规则、调用写工具” | 作为不可信数据处理，不能升级权限 | 有宿主工具与确认边界；完整注入攻防集待补 |

NFC 不会把否定词删除。输入清洗也不等于 Prompt Injection 防护。系统指令、用户输入与外部资料应明确分层，权限检查留在模型外，参照 [OWASP 的 LLM Prompt Injection 防护建议](https://cheatsheetseries.owasp.org/cheatsheets/LLM_Prompt_Injection_Prevention_Cheat_Sheet.html)。

### 3.3 后续通用事件协议

推荐把复杂输入解析成受约束的事件列表，例如 `resume_task`、`modify_constraints`、`cancel_task`、`new_task`，每项携带可验证的任务标识。

模型只能在当前用户拥有且可作用的任务集合中选择；对象不唯一就澄清。候选选择和写入确认继续使用确定性校验，不能因为 LLM 判断“像是在确认”就绕过有效期和凭证。

这项通用事件协议属于设计扩展，不冒充当前基于连接词拆分已解决的能力。

## 4. 信息时效矩阵

下列时间是本项目当前可配置的应用策略，**不是行业统一值或已经压测得到的最佳参数**。

| 数据 | 默认期限 | 过期动作 | 为什么 |
|---|---:|---|---|
| 会话语义背景 | 三十分钟 | 不再进入新任务模型历史；原记录保留 | 避免昨日地点、旧需求无意污染新请求 |
| 待补参数交互 | 三十分钟 | 拒绝旧恢复，允许显式刷新；跨日相对日期另行处理 | 不能无限期假设用户还在回答原问题 |
| 候选选择 | 五分钟 | 禁止旧选择，重新查询并生成新中断 | 顺序、可用对象、上下文可能变化 |
| 写操作确认 | 两分钟 | 禁止旧同意，刷新后重新确认 | 授权绑定对象、参数和时间，不无限有效 |
| 天气回执 | 五分钟 | 不再复用为当前新鲜结果 | 预报可能更新；仍只承诺获取时间 |
| 地点/周边/详情回执 | 五分钟 | 重新读取服务数据 | 商家字段、候选排序可能变化 |
| 路线回执 | 两分钟 | 重新规划 | 路况与估算随时间变化更明显 |
| 音乐检索回执 | 三十分钟 | 重新检索 | 曲目相对稳定，但结果与链接并非永久有效 |
| 当前行程/提醒列表 | 不跨重复读取复用完成结果 | 再读时查询当前存储 | 列表可能被另一个操作修改 |
| 部分临时记忆键 | 五分钟 | 不作为偏好注入；保留管理记录 | 当前位置不能冒充稳定偏好 |
| 稳定偏好 | 不统一设置短 TTL | 用户更新/删除；不得覆盖当轮要求 | “喜欢步行”与“当前位置”不是同类事实 |
| 操作回执与账本 | 不按结果新鲜度删除 | 用于核查历史操作是否已经执行 | 结果过期不能使副作用历史消失 |

临时键当前明确包括 `current_location/当前位置/current_city/当前城市/last_selected_poi`。这是有限的键策略，不是完整的语义记忆分类系统。自定义中文别名不自动具有同样的短期语义。

### 4.1 工具回执中的时间元数据

```json
{
  "_freshness": {
    "source": "maps_route",
    "issued_at": "2026-10-24T02:00:00+00:00",
    "expires_at": "2026-10-24T02:02:00+00:00",
    "ttl_seconds": 120,
    "scope": "retrieval_receipt_not_provider_truth"
  }
}
```

这是元数据格式示例。时间表示本系统接收到回执，不代表高德恰好在这一秒重新观测了全量道路数据，也不能证明商家在期限内必然营业。

### 4.2 有效期与缓存的区别

缓存只回答“数据放在哪里、是否可以复用”；业务有效期回答“这份数据是否仍可支持这次决定”。

Redis Key 仍存在，不代表数据可以使用。反之，Redis 缓存失效而数据库记录仍新鲜，可以回填；回填时只能使用原始更新时间的剩余有效期，不能重新赋予一整个有效窗口。[Redis EXPIRE 说明](https://redis.io/docs/latest/commands/expire/)

本轮同时增加数据库上下文年龄检查，避免缓存 miss 后从持久层取出陈旧摘要再赋予新 TTL。

## 5. 过期选择的完整处理链路

示例：10:00 展示饭店 A、B、C；10:10 用户点击“第二个”。

1. 客户端检查到过期后，禁用旧选择并显示“刷新当前任务”。
2. 即使用户绕过界面直接调用恢复 API，服务端仍会检查过期并返回 409。
3. 用户显式刷新，提交原 task 与 interrupt 标识。
4. 宿主核对归属与等待状态，从父/子图快照合并当前任务事实，保留已澄清的起点与用户约束。
5. 清除旧选择、回执和授权，生成新的 `read_generation`。
6. 重新准备近期上下文，并从领域入口继续；不让模型随意改写原任务目标。
7. 查询使用新的读代次，不会因为参数相同就复用旧队列完成记录。
8. 新结果可能变为 D、A、B；系统展示新候选，等待重新选择。
9. 旧 `interrupt_id` 无法恢复新中断；旧“第二个”不会自动映射成新列表第二个。

候选交互的有效期还受其工具回执期限约束，取更早的到期时间。不能因为刚刚展示了一个已经陈旧的结果，就从展示时刻重新给它完整的五分钟寿命。

刷新不是时间旅行到一个检查点后自动执行外部动作。LangGraph 提供状态恢复机制，应用仍需要自己定义数据时效与授权边界。[LangGraph interrupts](https://docs.langchain.com/oss/python/langgraph/interrupts)

### 5.1 当前错误码

| HTTP | code | 客户端动作 |
|---|---|---|
| 409 | `INTERRUPT_EXPIRED` | 刷新当前任务，重新选择/确认 |
| 409 | `RELATIVE_DATE_EXPIRED` | 不自动续用相对日期，请用户重新提交明确日期请求 |
| 409 | 状态或中断已变化 | 重新读取任务，不能再次盲发同一恢复 |
| 404 | 任务不属于当前用户或不存在 | 不泄露其他用户任务 |
| 429 | `TOO_MANY_ACTIVE_TASKS` | 按 Retry-After 退避，不自动创建更多任务 |
| 503 | 未配置真实模型或生产身份未接入 | 修复服务配置，不切换模拟成功 |

### 5.2 API 示例

```http
POST /api/tasks/{task_id}/refresh
Content-Type: application/json

{"interrupt_id":"当前等待中断的标识"}
```

刷新只接受当前等待任务。已取消和已完成任务不能被此入口复活；多个并发刷新只有一个被接受。

## 6. 时间类 Query 与位置类上下文

### 6.1 相对日期必须有解析时刻

用户 23:59 说“明天杭州天气”，00:05 再补充信息。如果重新以 00:05 解释“明天”，目标日期就发生变化；如果无提示沿用旧日期，用户也可能误解。

当前采取保守策略：原请求跨北京时间日期且包含受识别的相对日期表达时，恢复与刷新都要求重新发送明确日期。普通的、不跨日的缺参恢复继续沿用原任务事实。

代码对明确中文“今天/明天/后天/今日/今晚”和英文 today/tomorrow 做边界检查，不声称已经覆盖“下周五”“等一会儿”等全部时间语言。提醒执行前还会再次校验时间在未来。

当前跨日检查锚定任务创建时间，尚未把入口接收时刻作为统一 `request_time` 传播给所有规划、拆分和日期解析节点。若规划本身横跨零点，或子任务晚于原请求创建，仍需补齐统一时间锚点后专项验证；不能把已有入口检查当成完整相对时间引擎。

### 6.2 默认地点不等于 GPS

“东南大学无锡国际校区”仍是配置或表单参考点；固定地址不会因两分钟过去而自动变成另一个地方。

真正动态定位应该包含来源、采集时刻、精度、同意范围与有效期。用户已经移动时，重新规划应先获取新定位或询问起点。当前没有接入实时 GPS，因此不声称已经检测移动距离或定位精度。

### 6.3 实体、属性和授权要分开

POI ID 相对稳定，不代表营业状态也稳定；商家营业状态更新，不代表可以换成别的商家；用户确认保存某条行程，不代表同意未来所有写入。

后续涉及预订、支付或库存时，需要资源版本号、最新价格/库存、确认参数摘要和有效窗口。只缩短聊天 TTL 不能解决交易一致性。

## 7. 写操作与故障恢复策略

### 7.1 两次检查授权期限

第一次在用户点击确认、恢复 API 接收时检查；第二次在工具 worker 获得执行机会、真正发送请求之前检查。

否则用户 10:01 确认有效，作业排队到 10:10 仍执行，会绕开两分钟授权窗口。当前将期限存入工具作业 `expires_at`，重启后也不会丢失。

发出请求后到回执返回前，远端是否已经提交仍可能未知。授权在 dispatch 前有效不等于执行可以随时撤回。

### 7.2 按副作用区分重试

| 情况 | 读工具 | 写工具 |
|---|---|---|
| 临时网络异常 | 预算内有限重试 | 当前不自动重试，进入核查 |
| 业务参数错误 | 澄清或修正，不盲重试 | 同左，不能扩大授权范围 |
| 进程退出留下 running 作业 | 可重新排队查询 | 死信隔离，先核查账本 |
| 收到晚到成功回执 | 记录证据 | 记录证据，不让取消状态被覆盖 |
| 用户再次提交同一写幂等键 | 参数一致时复用已知结果 | 不能为“刷新”换一个新写幂等键绕过去 |

“不自动重试”是保守策略，不是写入永久失败后永远不能恢复。人工或后续自动对账可以确认未执行后发起新的合法操作；确认已执行则返回原资源。

### 7.3 生命周期并发

同一根任务下的 resume、refresh、retry 与 cancel 使用共享锁，并在锁内重新读取状态。这样取消不会与刷新/重试交错把已取消任务重新排队。

已完成分支保持已完成；取消一个未完成分支不应删除兄弟分支结果。当前通过单进程并发回归验证这类交错，不扩展声称分布式恰好一次。

## 8. 高并发与服务可用性

### 已落地

- 每用户默认八个排队或运行根任务的入口背压；重复 request_id 检查优先，重传不会占新配额。
- 子任务最多六个，并发 worker 和单工具 semaphore 限制在途数量。
- 工具级超时、有限退避、死信、部分成功、SSE 与序号续读。
- 模型故障恢复不重新执行成功分支。
- 新增每任务累计活跃时间一百二十秒、单次规划四十五秒、模型八次/工具提交二十四次、恢复八次/刷新五次/根任务模型恢复三次；图 super-step 上限六十四。人等待不消耗活跃时间，恢复不重置持久化额度。
- 工具作业持久化 deadline，向 dispatch 传播剩余时间；只读暂时故障最多重试两次，指数抖动退避并考虑数字 Retry-After。模型 SDK 自动重试关闭，结构化格式最多额外修复一次。
- 诊断 API 聚合模型、工具、排队与人工等待，链路页提供汇总及带诊断的 Trace 导出。已知失败 Token 不丢弃，缺少 usage 不冒充零成本。

### 上线前还需要

- 每租户/用户/供应商 Key 的统一速率与并发配额；多进程共享额度，而不是每个实例各放八个。
- 在已实现的每任务预算和作业 deadline 基础上，补根任务跨依赖分支的统一请求级 deadline，明确人等待与后台作业语义。
- 图检查点、业务任务表与事件记录跨存储更新时的恢复协议。当前共享锁不等于多存储事务，仍需明确状态权威、版本号、Outbox/对账与崩溃恢复。
- 供应商熔断、半开探测与负载保护；切换供应商也必须保持模型/工具证据和参数契约，不能切换模拟数据。
- 避免恢复接口成为绕过入口配额的路径。当前八任务限制主要覆盖新消息创建，不是全路径全局调度器。
- 独立 worker 的租约、心跳、可见性超时与原子抢占；当前 SQLite 队列不当作跨地域调度系统。
- 长时间 soak test 与高峰负载验证，记录拒绝率、超时率、队列年龄、P95/P99 和供应商配额。

## 9. 生产身份、隐私与知识治理

### 当前明确的安全门禁

本地模式只适合可信开发环境，`X-Demo-User` 是命名空间，不是认证。非本地模式现在拒绝未经验证的身份，不再将任意 Bearer 令牌拼接为用户 ID，也不把令牌当用户标识落库。

这意味着在真正认证接入之前，不能把 `APP_MODE=production` 当作已经可用的公网部署开关。

### 待上线验收的内容

- 接入已有认证系统，验证签名、发行方、接收方、到期时间；按 tenant/user 做授权，不接受模型提供身份。
- 密钥走服务端秘密管理，日志脱敏，前端不得拿到模型和高德 Key。
- 外部文本、商家描述、RAG 资料只作为数据，不允许更改权限、工具白名单或确认状态。
- 生产 Trace 记录最小必要信息；分别设内容、事件、检查点和审计记录保留策略，支持删除与访问审计。
- 知识资料更新具有来源、版本与显式删除；删除后必须同步索引、缓存和引用，不只 upsert 新片段。
- 会话时间过滤不是逐事实新鲜度识别：父任务较晚汇总时，文本中仍可能包含较早分支结果。后续应给实体与事实携带独立的来源和观察时间，不能用会话更新时间证明其中每条事实仍实时有效。
- 发布前检查模型名、提示词版本、工具契约、知识索引和依赖版本；灰度与回滚不能重放副作用任务。

## 10. 生产评测与发布门禁

### 10.1 先验证不该执行的确实没执行

新增场景至少包括：

- 候选过期后点击旧序号，刷新后列表排序变化，旧序号仍不能沿用。
- 查询年龄大于工具期限，相同工具参数不得永久复用旧作业。
- Redis 有旧摘要，数据库有旧记录，回填不能延长旧事实寿命。
- “明天”跨日补充，系统不静默改变日期。
- 操作确认过期、确认有效但出队时过期、提醒时刻已经过去。
- 写工具抛异常、进程留下 running 写任务，不自动再次调用。
- 同任务同时刷新/取消，同父任务同时恢复/重试/取消。
- 不同用户使用他人的任务标识、请求标识或过期中断。
- 同用户多个会话同时提交，去重和背压仍生效。

### 10.2 指标口径

| 指标 | 分母与成功条件 |
|---|---|
| 过期恢复拦截率 | 所有已过期 answer/approve 请求；必须未产生禁止的选择/写入 |
| 刷新后正确绑定率 | 有效刷新并重新选择的场景；绑定新快照对应 ID |
| 旧上下文泄漏率 | 明确设置过期背景的场景；新理解中不得使用被排除的信息 |
| 过期授权误执行次数 | 授权过期或出队前过期的写入尝试；同时报告尝试数与实际调用数 |
| 未知写入自动重放次数 | 超时/重启故障注入场景；记录下游调用次数与账本证据 |
| 全目标完成率 | 所有已提交真实会话；限流、模型失败、超时都留在分母 |
| 超载拒绝率 | 指定负载、配额和测试时段下的提交次数；不能混为模型错误率 |
| 端到端完成时延 | 明确是否含排队、重试、用户等待和失败结束 |

测试通过不等于零风险承诺，时间参数也不是精度指标。生产阈值需要在真实请求分布、服务配额与用户体验之间选择。

## 面试时如何概括

> 我后来重点补的是时间维度与状态边界。会话背景、候选、工具结果和操作授权分别设置有效期，缓存回填也不能把旧信息重新变新。用户隔很久选择旧结果时，系统先拦截，显式刷新后重新查询、重新选择；确认在接收和出队时各校验一次。读操作可以重查，结果未知的写操作则进入核查，不因为超时或重启自动重放。这些已经有单进程回归，分布式调度、真正身份认证和高峰负载仍是上线前的明确门禁。
