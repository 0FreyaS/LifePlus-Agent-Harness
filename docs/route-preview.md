# 路线结果：对话内地图与完整路线页

更新日期：2026-10-26。

## 1. 用户能看到什么

- 对话中直接展示真实高德地图及道路轨迹，而非仅输出 URL。
- 显示起点、终点、出行方式、距离、预计用时，以及服务实际返回的收费信息。
- 通过分段按钮切换驾车、步行、骑行；通过刷新图标重新规划当前方式。切换固定复用已确认起终点坐标。
- 高德返回多个可用方案时，选择方案同步更新距离、用时、收费、道路轨迹与步骤；没有多条结果时只展示实际可用方案，不补造路线。
- 地图可以缩放、恢复完整路线视野，点击展开进入 `/routes/{task_id}?job={job_id}`。
- 路线步骤可展开查看，完整路线页同时展示地图与步骤。
- 重新进入历史会话后，从持久化工具回执恢复地图；多任务按根任务与子任务标识绑定，不能把旧地图挂在最新回答下。
- 本地生活页规划到饭店、KTV、电影院等商家的路线，复用同一地图展示。

**明确边界：** 当前是高德官方静态地图图片与路线回执的展示界面，不是高德 JS SDK，也不包含网页内实时 GPS、语音或逐转向导航。用户点击“在高德中导航”才打开高德入口，不能声称已经启动设备导航。未申请或使用浏览器位置权限。

## 2. 为什么使用此方案

当前已有高德 Web服务 Key，已实际验证可调用官方静态地图服务。使用服务端图片代理可以在不另配 JS SDK Key、不把现有服务端 Key 下发浏览器的前提下，将地图、标注和道路轨迹嵌入当前应用。

没有使用一个可能被浏览器拒绝嵌套的第三方导航 iframe，也没有绘制假地图或把起终点直线冒充道路。后续若需要拖拽地图、定位跟随和实时路况交互，应另行接入适合的地图 SDK、授权与配额，不把当前快照界面称为实时导航。

协议依据：[高德静态地图](https://lbs.amap.com/api/webservice/guide/api/staticmaps)、[高德路径规划 URI](https://lbs.amap.com/api/uri-api/guide/travel/route)。

## 3. 真实数据链路

```text
用户输入路线需求
  → LLM 结构化理解 → 地点检索 → 必要时用户选择
  → maps_route 返回真实距离、用时、步骤与 polyline
  → 持久化工具回执，保留道路坐标 geometry
  → session/routes 为历史消息提供轻量附件索引
  → 对话组件按 root_task_id/task_id/job_id 绑定地图
  → 后端检查用户归属，从该回执构建静态地图参数
  → 高德返回地图图片 → 浏览器通过受鉴权的 Blob 展示
```

道路坐标来自高德 route steps，不由 LLM 生成。相邻重复点去重后最多保留 1500 点；地图请求使用最多 100 个真实轨迹点形成概览。展示可能因采样概化，不作为精细转向或道路通行保证；完整出行指引以高德为准。

几何坐标及备选路线列表不传入生成回复的模型上下文，避免地图细节占用 Token，或让模型自行挑选与界面默认不一致的方案。当前主方案的业务结果、距离、用时和步骤仍可供模型生成有依据的答复。

历史回执没有几何数据时，只标起终点并提示，不凭空连接成“道路”。失败回执、模拟回执和取消任务不包装成真实高德路线。

## 4. 接口与权限

| 接口 | 作用 |
|---|---|
| `GET /api/sessions/{id}/routes` | 当前用户会话的轻量路线附件索引，每个任务取最新有效成功回执 |
| `GET /api/tasks/{id}/route?job_id=...` | 指定路线快照的详情，含步骤、来源、有效期、缩放基准与官方导航入口 |
| `GET /api/tasks/{id}/route/map?job_id=...&zoom=0&large=false` | 后端代理真实 PNG；zoom 仅允许 -4 至 4，实际缩放限制在服务范围内 |
| `GET .../route?job_id=...&option=1` | 选择同一真实回执中的备选方案；图片接口也接受同一个 option；只允许 0～4 范围内的实际方案 ID |
| `POST /api/tasks/{id}/route/replan` | 提交 `{job_id, travel_mode, request_id}`，创建独立的 live 路线重规划任务，立即返回 202 和 task_id |

图片不是带用户参数的公开直链。前端 fetch 仍携带当前身份头，再创建 Blob URL；组件卸载或切换视图会取消请求并回收 Blob URL。

每次读取都先查任务归属，再查图片缓存，因此命中缓存不会绕过权限。浏览器响应为 private 缓存；后端最多缓存 24 张、每张 120 秒，最多三个并发地图请求；排队与请求有总超时，图片大小有上限。

只请求固定的高德静态地图地址，不接受前端传入任意远端 URL。上游错误或非 PNG 返回不会原样转发；错误响应不回显带 Key 的请求地址。地图失败不改变原工具执行状态，也不会回退到假图片。

本项目开发身份头仍是本地命名空间，不是真正的公网认证。地图接口沿用已有用户隔离，不代表已解决整个项目的生产身份接入。

## 5. 时效与完成依据

路线回执沿用应用侧有效期。过期仍可作为历史快照展示，并明确提示“请重新规划后出行”；加载一张新的底图不延长旧路线回执的有效期。

地图与回复都以实际工具回执为依据。工具成功并不代表用户已经到达目的地，也不代表高德客户端已经开始导航；商家路线不能证明商家实时营业或预订成功。

## 8. 出行方式切换与备选路线

切换方式不只是改变文案或将步行时间按比例换算成驾车时间：

```text
用户点击“驾车 / 步行 / 骑行”
  → POST route/replan，提交原回执 job_id、出行方式及去重 request_id
  → 后端验证源任务与回执属于当前用户，读取已确认坐标
  → 新建独立任务，结构化参数进入 LangGraph 的 navigation_route 流程
  → Harness 校验坐标/枚举，Tool Queue 调用真实 MCP maps_route
  → 校验回执方式、起终点、距离与用时，持久化结果与执行事件
  → 客户端等到任务完成后替换卡片；失败时保留原卡片，提供错误与执行链路
```

该点击已经给出了确定意图和端点，因此不再调用模型重新分类或查一次同名地点，也不需要模型生成固定结果回复。它仍经过图节点、工具白名单、队列预算与结果校验；不是直接从浏览器调用高德，更不是绕过 Trace。当前接口沿用已有 live 模式准入配置。

重规划只接收源回执与方式，不接受前端覆盖 origin/destination。重复 request_id 返回同一任务，不能使用同一个 ID 切换为不同方式。旧回执保持不变，新任务可以在历史对话和执行链路中查到。过期快照可以作为用户确认的固定端点参考，但新路况、用时和几何必须重新向高德获取。

驾车使用官方多策略 `strategy=10` 与 `extensions=all`；工具保留高德返回的最多五个有效 paths，每个方案分别持有几何、步骤和指标。当前项保留在旧顶层字段，备选项保存在 alternatives 中。步行、骑行是否有备选由真实服务决定，不强求三条。

选择同一回执的方案只读取持久化的不同 path，不重新算路；图片仍走相同鉴权接口。详情页 URL 带 option，刷新保持当前方案。外部高德 URI 只传端点和出行方式，不能保证锁定网页中选中的第几个 path；进入高德后可能按最新路况重新规划。

切换期间保留原地图与方式标题，避免将旧步行轨迹标成新驾车路线；新回执、地图和步骤必须使用同一个 option_id。组件卸载、切换源任务和过期异步响应均不能覆盖其他任务的结果。等待有 90 秒客户端预算，服务器任务仍受 Harness 自身预算约束；客户端等待超时不等于服务端一定失败，可继续查看任务链路。

## 9. 用户自主选择与默认方式

路线卡片同时保留驾车、步行、骑行三个选择，并独立展示“路线方案”选择区。当前方式有显式勾选和 `aria-pressed` 状态；当前请求对应的默认方式排列在前，其余选项不会被隐藏。用户仍可切换任何方式、选择服务返回的其他方案，系统不会自动启动设备导航。

默认方式按当前用户输入确定：例如“从杭州东站骑行到西湖”必须先生成骑行回执，接口返回 `default_travel_mode=bicycling`，`mode_choices` 首项为骑行且仅一项 `is_default=true`。宿主层对明确肯定的“骑行/骑车、步行/走路、驾车/开车”做轻量约束校验，优先于模型误填的合法默认值。它只约束出行方式，不代替模型识别地点和整句意图，也不从历史消息里扫描“骑行”来覆盖当前请求。

“不要驾车，骑行过去”不会把否定的驾车设为默认；“驾车改成骑行”按明确更正选择骑行；“骑行和驾车哪个更快”不由关键词规则擅自判成某一个确定偏好。未明确方式时保留合法结构化槽位；确实缺失时沿用当前配置的驾车默认值，但三个选项始终开放。

这里的“三种可选方式”不表示已经同时为三种方式算路。初次只请求默认方式；用户点击另一方式后，基于已确认坐标真实规划，成功才改变所展示的地图、距离与步骤。未查询的方式不填估算用时，失败时不把旧图改名冒充新方式。每种方式有几条方案取决于高德实际返回，不复制一条路线凑数量。

## 10. 选择入口的可发现性修正

用户提供的页面截图中，旧版卡片从标题直接进入地图，没有出行方式或方案按钮。接口检查确认，该会话实际有驾车三个方案及骑行结果。此前仅依据源码、构建和 `Cache-Control: no-cache` 就认为服务已提供新组件，证据不足；后续直接检查 5176 的 `/src/RoutePreview.tsx` HTTP 响应，确认运行中的 Vite 仍返回旧转换模块，缺少 `selectionOnly`、出行方式与方案选择逻辑。磁盘代码与运行服务不一致是此次按钮缺失的已确认原因，具体原生文件监听失效的触发条件尚未确定。

现在除了消息内地图卡片，对话标题下还独立提供 **路线选择** 区，不依赖历史消息与地图附件的匹配，也不随消息滚动消失。它直接使用当前会话最新的真实路线索引，展示全部出行方式与实际方案，支持查看地图。顶部选择与对应消息卡片共享选择结果；重新规划仍经过原有真实队列接口。路线索引加载失败会明确提示并提供重试，不再让路线接口失败阻断整个会话历史的更新。

本次前端 **43 项测试通过，生产构建通过**；增加独立选择区的静态渲染与 AST 位置测试，确认三个出行方式和三个实际方案都能渲染，且该区位于消息滚动容器之外。这些检查不等于浏览器视觉与点击验收。

已打开很久且没有更新的标签应重新加载一次新入口，例如当前会话 `/chat/98d97b2e-72b6-4793-b5be-1be67695c21f?ui=route-picker-v4`。该查询参数仅用于区分重新打开的入口，不是身份参数，也不改变后端数据。
