2026-10-23 完成 8 类、每类 30 条的首版评测。首轮 232/240 条通过，修复后的完整复测 240/240 条通过。这里是不同测试层的断言总数，不是线上用户任务完成率，也不代表完成了 240 个真实模型与外部工具的端到端会话。

## 发现并修复的问题

### 1. 模型领域正确，动作名称不符合内部契约

`single_task-01` 的天气动作返回 `get_weather`，而标准动作是 `weather_lookup`；`single_task-29` 的闲聊返回 `self_introduction`，而标准动作是 `chat_answer`。这些是动作契约不一致，不等同于调用了错误业务工具。

修复：对天气、导航、音乐、健康、闲聊这些只有一个可执行动作的领域，由宿主统一规范化为标准动作。行程与本地生活有多个动作，仍需识别并校验具体动作，不能统一覆盖。新增别名输出回归用例。

### 2. 无参数请求返回 `slots: null`，触发解析异常

`single_task-30` 请求讲故事，模型返回领域为 chat、槽位为 null，Pydantic 原先拒绝解析，导致一个无需工具的闲聊请求失败。

修复：在结构化解析边界将 null 归一为空对象，再执行字段验证；不把任意字符串、非法数字等错误内容强行转为合法参数。新增 null 槽位测试。

### 3. 确定性补充逻辑覆盖了模型正确的起点

`slot_extraction-06`：用户说“从杭州东站步行到西湖”，规则把起点提取为“杭州东站步行”，覆盖了地点语义；原先也没有把这类明确起终点表达全部标为路线请求。

修复：显式起终点解析把步行、骑行、驾车等交通动词纳入连接结构，保留纯地点；明确 `从 A 到 B` 的请求进入路线流程。增加步行、骑行、驾车及“步行街”地点名对照测试。

### 4. 错误确认凭证没有写入，但失去继续确认的位置

`recovery-04/14/24` 分别对应保存行程、创建提醒、取消提醒。错误 `operation_key` 不会执行写工具，但图最终返回 failed，且没有待恢复的 interrupt；原先文案说“重新确认”，状态却无法继续确认。

修复：错误凭证在授权节点中重新 interrupt；有效确认后才调用写工具。三种动作均检查：错误凭证阶段零次写入、存在真实待确认中断、再次有效确认后恰好执行一次。复测断言比首轮更严格，而不是把失败条件放宽。

### 5. 快速连续调用触发高德限流

`real_tools-12` 返回 `AMAP_10021 / CUQPS_HAS_EXCEEDED_THE_LIMIT`。这是供应商限流，不是之前的 30001，也不是“没有找到北京站”。

首轮失败没有删除、重标或计为通过。复测在每次 MCP 调用结束后等待 0.4 秒再发下一次，30/30 通过；等待时间不记入工具执行耗时。**这只是受控的评测负载，不代表生产已实现跨进程全局限流，也不证明高 QPS 稳定性。**生产仍需按实际 Key 配额制定限流与总预算策略。

两个运行使用相同 v1 数据集，但实现、错误凭证断言和真实工具请求节奏不同，因此不是严格受控的性能 A/B 实验。

## 时延与成本实测

以下为完整复测的阶段耗时，失败和重试不剔除。真实模型使用生产的单次 25 秒超时、1 次 SDK 重试，评测外层有 75 秒保护；没有模拟用户等待时长。

| 测试层 | 平均 | P50 | P95 |
|---|---:|---:|---:|
| 单任务意图理解 | 6.930 秒 | 6.174 秒 | 12.679 秒 |
| 多任务拆分与依赖规划 | 11.533 秒 | 8.492 秒 | 40.345 秒 |
| 槽位提取与规范化 | 9.866 秒 | 9.533 秒 | 17.113 秒 |
| 模型理解 + 缺参图节点判断 | 11.956 秒 | 8.532 秒 | 22.157 秒 |
| 真实 MCP 工具混合组 | 0.209 秒 | 0.220 秒 | 0.312 秒 |

这些不是可相加的串行阶段：单任务、槽位、澄清是不同数据组的独立测量。工具混合组含极快的本地行程读写，也不应称为“高德接口平均时延”。

**正确性通过不等于性能达标。**多任务规划单阶段 P95 已达 40.345 秒，不能继续沿用“多工具任务 P95 ≤8 秒”的完成时延说法。首轮该阶段 P95 为 11.192 秒，跨轮波动明显；本轮没有供应商内部 Trace，不能把等待时间都归因为模型推理，也不能认为功能修复导致了时延变化。

下一步应单独测首增量与最终完成时间，记录调用尝试/网络/供应商等待，增加统一端到端 Deadline，再比较更轻量的结构化路由与规划方案；并行工具可以缩短分支等待，但不能消除前置规划调用的长尾。

完整复测实际收到 120 次模型响应，用量为 **155,325 input tokens + 11,866 output tokens**，没有缺失 usage 的响应。只统计供应商返回用量，不据此编造价格；也不称“每成功业务任务成本”，因为业务端到端并未完整评测。

## 补充回归

后端完整回归：**116 passed、1 skipped，13.05 秒**。其中多任务 API 回归 36 条、评测与新缺陷测试 16 条；其余覆盖地图参数、真实本地存储、工具适配、图流程与运行组件。默认跳过的独立 live 测试入口，不代表本轮没有真实调用：上述 30 条真实 MCP 已单独执行。

API 回归检查了实际同时在途、慢分支不阻塞快分支、依赖完成后再启动后继、部分成功、同会话等待时接新任务、一句话恢复选择并创建新任务、重复请求、SSE 增量及断线续传。多数使用受控模型/工具，不能算成真实模型准确率。

## 本轮不能声称的能力

- 不能将 240/240 写为线上端到端任务完成率 100%。数据为人工合成，模板变体存在相关性；每类只有 30 条，澄清正例仅 15 条。
- 没有对 30 个多任务全部执行真实外部工具并核对最终用户目标，也没测 30 个真实自然语言补充后的完成率。
- 没有进行真实 GPS、实时商家营业/排片/预订校验，没有实际音乐播放或设备操作。
- 没有实测 PostgreSQL/Redis/MySQL 故障恢复、长时间压力、真实进程重启、跨实例恰好执行一次。
- 没有人工 Rubric 或独立 LLM judge 评分，不能沿用 4.2/5；也没有针对回复事实性给出“虚假完成率 ≤1%”结果。
- 运行中取消无法撤销已经发生的远端副作用。迟到成功回执保留在取消状态下，不能把它算成“远端肯定没有执行”。

下一轮应以脱敏 bad case 和更复杂的多轮表达补充 v2，按模板/会话分组隔离，冻结本轮 v1；不要用当前测试集反复调提示词后当作独立验证结果。
