# 任务完成率优先：验收口径与可靠性改进

## 不再用节点通过率替代任务完成率

此前 240 条分层评测回答的是“路由、槽位、图节点和工具分别是否满足断言”，不是用户目标是否最终完成。本轮新增独立的端到端评测：

| 会话类型 | 数量 | 完成要求 |
|---|---:|---|
| 单任务 | 30 | 从自然语言输入到真实回执、结果交付；写操作需确认且可查到落库记录 |
| 多任务 | 30 | 每个明确请求的子目标都完成；不得少拆、多拆或遗漏依赖数据 |
| 澄清后完成 | 30 | 缺少城市、参考地点或起点时先中断，接收补充后实际完成；含等待选择时追加新任务 |

另有 6 条“不带逗号的复合回复”专项回归，与上述 90 条分开记录。

**会话任务完成率 = 全部约定目标均满足验收的会话数 / 全部已提交会话数。**

部分成功、一直等待、超时、外部服务失败、参数错误和缺少真实证据都不能计为整条会话成功。同时保留分目标完成数，避免把“天气成功、导航失败”既算全成功，也抹去已完成的有效工作。

## 端到端如何执行

实际链路是：

`HTTP handler → 协调器 → 真实模型路由/规划 → LangGraph 父图及子图 → interrupt/resume → Tool Queue → MCP → 实际服务/数据库 → 结果回复 → 目标核验`

HTTP 使用 ASGI transport 直接访问实际应用 handler，没有伪造 handler 返回，也没有替换模型或工具。高德与音乐仍通过真实网络请求；行程、提醒写入专用 `runtime.sqlite3`，不碰正常用户数据库。该方式未测浏览器、TCP 与反向代理层开销。

每条使用独立用户、会话和请求标识。用户模拟器只提供预先约定的城市/起点/参考地点、选择工具实际展示的候选，以及批准原本请求的写操作。不注入意图、不直接修改图状态，也不把正确答案放到模型提示词中。

完成判断不能只看 `status=completed`：

- 天气：工具参数城市/日期与目标一致，回执包含相应城市和日期的天气字段。
- 音乐：检索关键词正确，实际候选非空，选中的歌曲有详情链接；不把检索当作播放。
- 本地生活：类别、参考地点正确，候选非空，详情必须绑定用户选中的 POI ID。
- 导航：确实取得路线距离、时长及链接，路线终点绑定选中 POI 的坐标，明确起点不丢失。
- 保存结果：先有用户确认，再有写工具回执，并能按用户与资源 ID 查到数据库记录。天气后保存的依赖任务还需核对实际保存的城市、日期、天气字段来自上游回执。
- 多任务：用不同叶子任务分别匹配每个目标，检查数量；不允许一条成功回执覆盖多个未执行需求。
- 闲聊：只能程序化检查文字交付、请求实体和不误调工具；不声称完成了人工事实性评分。

运行结果逐条保存 Query、目标、用户交互、根/子任务状态、失败原因及 Trace 文件，完整 Checkpoint、工具队列与写入账本留在隔离数据库中。

## 本轮代码补强

### 结构化输出校验失败后有限修复

历史失败中存在缺少必填字段等格式错误，之前会直接结束任务。路由和多任务规划现在只对 `OutputParserException`、Pydantic `ValidationError` 增加一次重新输出机会；保留原始用户请求和约束，不猜参数、不切换成 demo。

第二次仍失败就明确结束，不无限循环。供应商超时、认证错误等不进入这个修复循环，也不会重新执行已经产生副作用的业务工具。图内路由可以记录 `model.structured.invalid` 诊断事件。

规划阶段还提前验证多动作领域的动作名与可用绑定路径，避免执行到保存结果时才发现 `weather.tool_result` 这类不存在的路径；有效路径是 `selected/route/result/slots`。

### 复合回复不再依赖逗号

例如等待城市时收到 `无锡同时搜索周杰伦的歌曲`：

1. `无锡` 只交回原任务的城市澄清节点。
2. `搜索周杰伦的歌曲` 创建独立任务，拥有自己的 Thread、Checkpoint 与中断。
3. 原任务继续查天气，新任务搜索歌曲，两者均在端到端目标列表中核验。

同样支持 `第二个顺便查杭州天气`。仅在明确连接词后出现新命令时拆分；`同时音乐餐厅`、`无锡，同时不要播放歌曲` 不因包含连接词就创建新任务。

### 地址歧义展示真实候选并绑定坐标

路线工具若返回多个起点/终点，原先只让用户重新输入文本，候选信息没有展示出来。现在用工具返回的真实候选发起 selection 中断，接收索引、序数或唯一匹配名称后，把选中坐标写回相应起点/终点再规划路线。

导航、音乐、本地生活以及地址候选使用一致的选择解析，非法索引或布尔值不会被当成“第一个”。不从 LLM 的地理常识中编造地址和坐标。

### 依据回执决定是否能宣布完成

新增 `verify_execution()`，在回复前检查关键业务回执并写入 `result.verified` Trace 与 Checkpoint：

- live 模式不接受标为 simulated 的结果；
- 有目的地搜索结果不等于已经取得路线；缺少路线距离、时长或 live 路线链接会失败；
- 天气缺少城市、日期或天气字段不能宣布成功；
- live 写入只有 saved/scheduled 文案而没有资源 ID，不能宣布已保存；
- 歌曲缺少链接、商家详情 ID 不一致等会被识别为证据问题。

空清单是有效的清单查询结果；空检索不代表找到了匹配项，记录 `positive_result=false`，不捏造结果。文本回复只标记 `text_delivery_only`，不冒充事实已核验。

这个运行时检查是“内部契约与证据完整性检查”，仍不能独立证明用户意图完全正确。端到端测试还使用独立标注目标核对城市、日期、关键词与依赖内容，两层不能混为一谈。

## 复跑

在项目根目录执行：

```bash
.venv/bin/python -m evaluations.completion_dataset

# 90 条真实端到端会话，读取现有真实模型与高德配置
.venv/bin/python -m evaluations.completion \
  --output evaluations/runs/my-completion-run --concurrency 3

# 6 条无标点复合回复专项
.venv/bin/python -m evaluations.completion \
  --dataset evaluations/data/completion-compound-v1.jsonl \
  --output evaluations/runs/my-compound-run --concurrency 2

.venv/bin/python -m pytest -q --junitxml=data/completion-regression-tests.xml
```

目录必须是新的，防止覆盖旧证据。默认每条会话有 210 秒预算，包含实际模型生成、工具重试与自动交互；不存在真实人工思考等待，不能把它直接当作生产用户感知时延。超时保留为失败，并取消仍在运行的任务。

报告文件：`report.md`、`summary.json`、`results.jsonl`、`traces/*.json` 和 `runtime.sqlite3`。人工设计的小样本、固定选择策略与预设回答不能代表全部真实用户行为，也不证明生产 SLA。
