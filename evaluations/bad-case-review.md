### 5.2 归因方法：先找最早偏离点，再验证原因

我们采用的是**可复核的分层排查流程**，不是看到报错就归因“模型不够聪明”，也不是已经上线的全自动根因分析系统。

1. **保存原始失败现场。** 保留case_id、原Query、期望目标、会话/任务标识、配置及默认值、模型与思考参数、源码版本、候选快照、结构化输出、每次attempt、工具job/回执和最终状态。公开归档只放脱敏资料，私有数据库和Key不复制。现有各实验记录完整度不同，缺失信息明确标为缺失。
2. **先核对评测前提。** 检查时间、城市、默认位置、工具模式、候选有效期、动作能力是否与gold一致。标签要求“缺位置必须问”，但运行允许配置位置时，先记前提冲突，不直接算模型理解失败。
3. **按实际执行顺序找首个错误。** 依次看事件分类、目标规划、领域理解、参数准备、调度绑定、工具执行、结果回复；对比“预期输出”和“实际输出”。工具没启动，就不能归因到高德超时；前置计划失败引发后续missing_task，只记为传播症状，不另算多个根因。
4. **区分确定事实和推测。** 能从模型JSON证明的写“已确认”；只有最终错误码时写“待验证”。Schema合法、参数语义正确、工具成功、用户目标完成要分别看；不能只按completed状态判成功。
5. **做最小复现或对照。** 保持原Query和失败证据不变，先隔离组件。BC01用修复前后源码配对复现，BC07分开配置条件，BC09用无私有.env副本验证配置耦合。新诊断调用另存，不混入旧A/B结果。
6. **修原因并添加同类边界。** 优先修契约、数据来源、状态归属与约束，不用无限重试掩盖问题。加入近邻、否定、引用、同域多动作及不应写入的对照；测试集冻结，原失败永不改成成功记录。
7. **分层复验再关闭。** 先跑原失败和新长尾，再跑原完整集，最后验证真实工具、确认/取消、依赖写入与完整会话。记录修复前后通过数、P50/P95和全部Token；局部通过不能代替端到端、部署或生产闭环。

建议维护字段：`case_id / run_id / scope / query / expected / actual / first_bad_stage / root_cause / secondary_effects / evidence / fix / regression_cases / verification_status`。这是后续台账规范；不表示每一条旧Trace都已拥有这些字段，也不复制隐藏推理或敏感原文到公开日志。

### 5.3 BC01—BC03：结果绑定错误与无效修复

**怎么发现：** 全局规划专项30条只通过23条，失败集中在7条有结果依赖的计划。端到端`multi_completion-04/08/12/16/20`也失败，模型attempt停在plan，业务工具未启动。

**怎么排查：** 不能只看`OutputParserException`。原端到端输出截断了错误详情，因此保留原失败，另做规划诊断，观察到JSON可以解析，但生成了：

```json
{"depends_on":["t1"],"bind_slots":{"result":"t1.result"}}
```

右侧`t1.result`是前置证据，左侧却应该是接收任务的业务字段`details`。宿主原本拒绝非法接收字段，但给模型的Schema只说字符串映射，没有同样明确的允许集合。原修复又只说“不符合Schema”，模型不知道错在哪里，第二次仍可能输出同一非法字段。

**为什么不是其他原因：** 失败发生在队列提交前，不是地图、音乐接口失败。它也不是Jev领域分类错分；自动验收出现`wrong_domain / missing_task / missing_receipt`是整计划未落地的后果。原7条专项没有全部保留原始响应，不能声称它们每条都用了同一个非法键；后续配对记录才保留了各自字段和attempt。

**怎么修：** 将全局绑定接收字段显式化，来源限定为前置任务证据路径；按接收领域校验、检查来源直接依赖。明确`details ← t1.result`与`details ← t1.route`，不把非法键静默重命名。解析异常解包后，仅将安全的字段位置、错误类型及允许值反馈给一次受限修复，仍保留原请求和原预算。

修复后的新增长尾还有两个首轮坏例：`binding-search_save-02`和`binding-route_save-01`把`"title":"路上听"`或`"title":"骑行上课"`写进bind_slots。键可以接收标题，不代表值可以放字面量；该映射只能表达动态证据路径。校验准确指出`tasks.1.bind_slots.title`，第二轮将标题保留在query，只用`details`绑定真实结果，然后通过。

**修复效果：** 原7条0/7→7/7；新30条3/30→30/30，新增退化0条；原完整D04另测30/30。原7条attempt从14降到7，新30条从56降到32；新30条P50从2.081秒降至1.047秒、Token从46377降至37870。改善来自本批契约/校验/反馈/原子目标提示的组合，没有消融实验可将收益全归给某一句提示词，也不能外推整系统准确率。

**其他方案与取舍：** 不选择无限重试，因为错误契约会重复；不自动把result改成details，因为可能误改真正业务含义；不单纯依赖切换模型或增加思考预算，先修模型与宿主的不一致。当前仍关闭思考，相关比较不重新纳入本报告。

**证据：** [原规划/端到端逐条结果](测试数据集/结果记录/2026-10-30-01/README.md)、[独立诊断原文](../evaluations/jev/2026-10-29-deepseek/v1/diagnostics/planning-20261029.json)、[修复配对结果及源码快照](测试数据集/结果记录/2026-10-30-planner-binding-fix-01/README.md)。限制：修复后完整90会话、真实结果写入与写入授权尚未在本轮复测。

### 5.4 BC04：同域两个目标被合并，状态完成不等于需求完成

**现场：** `multi_completion-28/29/30`分别查询北京、成都、深圳天气，同时查看提醒和行程。预期三个独立目标：天气、提醒列表、行程列表；实际计划只有天气和“查看提醒和行程清单”两个目标。

**归因：** 检查`plan.completed`可见目标在规划阶段就被合并，不是并发任务丢失。领域节点一次选一个动作，实际只有`list_reminders`证据，没有`list_itineraries`证据；回复却说提醒和行程都为空。主因是目标拆分粒度错误，次生问题是回复扩大了已验证范围。这三条root都completed但目标验收不通过，也说明为什么要有独立目标检查；不能只统计系统状态。

**已做与未做：** 已补规划提示，要求同领域独立可验收目标分别成项，不能以领域数代替目标数。不把领域理解改成任意连续调用多个动作，以免模糊全局DAG与预算边界。原D04和新37条通过提供通用规划回归证据，**不是原3条天气＋提醒＋行程会话的专项关闭证据**；仍需用原Query验证三项目标、两种列表工具回执及回复范围。

**待补回归：** 同域双动作、独立三目标、“只查提醒，不查行程”、某一列表失败的部分成功回复；只有两项证据时不能宣称三项目标都完成。当前没有据此上调端到端82/90或下调结构化虚假完成3/85。

**证据：** [完整会话结果](测试数据集/结果记录/2026-10-30-01/全链路逐条结果.json)，按上述三个ID定位query、plan、目标验收及reply。

### 5.5 BC05—BC06：取消对象与引用语句的事件误判

**唯一取消：** `boundary04`只有一个待选歌曲任务，用户说“取消任务”。标准为取消该唯一任务，直接DeepSeek与Jev回退后的DeepSeek都返回“请问要取消哪个任务”。检查waiting、expected与decision，确认是事件决策未利用唯一性，而不是取消执行器失效；内部具体模型成因无法从输出证明。Jev在该条正确选择needs_llm，不等于整个方案通过。

**引用解释：** `boundary06`用户问`“第二个”是什么意思`，标准为新问题；两组却问“要选择七里香吗”。待选列表并未赋予用户这句话操作语义，错误在事件理解阶段，不是候选索引越界。应区分提及一个词和下达该词对应的指令。

**当前处理：** 两条在事件36条中都保留为失败，整组为34/36。本次没有改事件提示词、强制规则或重跑真实模型，不能写成已修复，也不能将换成llm_direct等同于解决这两个问题。

**拟解决与对照：** 候选唯一时，对完整且无新需求的取消句绑定唯一合法对象；多任务且无明确对象仍澄清，不靠“最近一个”猜测。对于引用/解释语句，在事件提示中给出最小对照：`第二个`应恢复，`“第二个”是什么意思`应新建，`第二个，顺便查天气`应恢复加新任务。不能用所有含“第二个”的句子统一规则处理。还需验证过期候选、取消后迟到回执和跨任务状态隔离。

**证据：** [36条输入及标准](测试数据集/06-文本事件/文本事件36条.jsonl)、[两组逐条事件结果](测试数据集/结果记录/events.jsonl)，定位boundary04、boundary06。未给出尚不存在的修复后成绩。

### 5.6 BC07：默认位置与澄清标签冲突，不应包装为模型提升

**发现与证据：** 首轮90会话70/90，通过Trace发现13条使用配置位置，而冻结标准要求追问位置；对应`clarified_completion-16`至`-28`。默认位置不是用户实时GPS，测试应显式说明是否允许回退。

**归因与处理：** 先认定实验前提不一致，保留原70/90审计与13个ID；另起完整90会话，在评测进程关闭默认定位以匹配标签，结果82/90。没有修改正常服务默认位置，也没有事后改标签或从两轮挑成功样本。

**不能得出的结论：** 不说修好了13个模型错误，也不将70→82归因为模型优化；两轮前提不同，且还存在其他失败。后续需维护“允许配置定位”和“必须用户定位”两套条件，并验证默认来源与过期规则。

### 5.7 BC08：RAG索引过期，先查数据生命周期而不是重排模型

**历史现场：** 删除文档后预期0个chunk，实际仍有2个；缩短文档后预期1个，实际仍有2个，两例都能检索到陈旧内容。

**归因边界：** 证据可确认索引生命周期存在残留，不能仅凭这两行结果断言当前实现的具体删除语句、事务或版本切换哪里出错，也不能归因给LLM、query改写或rerank。当前索引版本未复验，属于待关闭历史风险。

**拟修复方案：** 按document_id及版本维护chunk集合，更新时处理旧chunk，删除时撤销整个文档的可检索集合；需要连续可用时考虑版本切换，避免新旧片段同时可见。哪种方案落地应先核查当前存储后端，不在本次文档更新中虚构代码修改。

**如何验收：** 重放删除、缩短、重复更新、更新中断，再查chunk数量和旧文本是否可召回；加入无权限文档及并发更新对照。只看新文本能召回不足以关闭残留问题；当前无修复后分数。

**证据：** [历史2条原始失败](测试数据集/12-RAG时效/RAG历史删除与缩短2条.jsonl)与[数据说明](测试数据集/12-RAG时效/RAG历史删除与缩短2条.说明.md)。

### 5.9 BC10：增加分类器不一定提速，必须看全链路收益

**发现：** 直接DeepSeek与Jev文本过滤两组均34/36，事件P50却从0.852秒变成1.216秒；5例完整会话配对P50从5.452秒变成7.595秒。

**已采取：** 文本回复采用llm_direct，Jev过滤保持实验；当前策略另做5会话单臂复测5/5、7/7目标。领域Jev属于另一模块，保留其独立配对收益，不因为文本过滤失败就一并撤销。未知Token仍记未知，不通过补0制造节省。

**其他方案与边界：** 未来可减少前置提示体积、扩大可信纯回复接管或使用结构化卡片，但需要新冻结集和全链路配对才可切换。本结论是当时数据与配置下的取舍，不证明所有文本、模型或负载下直接LLM都更快。

### 5.10 后续关闭清单与面试表达
