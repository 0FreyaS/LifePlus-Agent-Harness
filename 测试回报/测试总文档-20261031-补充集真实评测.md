## 四、Bad Case

### A. 真实系统 Bad Case

#### Bad Case 1：取消任务被错误要求澄清

```text
等待任务：导航到东南大学
用户：取消导航任务
期望：route=cancel，target=导航任务
实际：route=clarify，请明确说明要取消的任务
样本：event-067
```

原因：取消表达已经包含明确的任务类型，但事件解释器没有把“导航”映射到等待任务的业务域。

改进方向：取消请求先提取目标域，再与等待任务建立候选匹配；单一候选直接取消，多候选才澄清。

#### Bad Case 2：候选选择无法识别自然语言变体

```text
等待任务：导航到东南大学
候选：南京校区、无锡校区
用户：第二个校区
期望：选择无锡校区
实际：没有找到唯一有效候选，要求用户重新点击卡片
样本：event-039
```

原因：选择解析没有把“第二个校区”归一化成候选序号，候选名称和序数表达没有进入同一解析路径。

改进方向：候选选择统一解析“第 N 个、第二个校区、选无锡、就南京那个”等表达，并在候选快照中完成索引校验。

#### Bad Case 3：“第二个是什么意思”被误判为澄清

```text
等待任务：搜索周杰伦歌曲
候选：晴天、七里香
用户：第二个是什么意思
期望：new，解释“第二个”对应的歌曲
实际：clarify，询问用户是否要选择第二个
样本：event-077
```

原因：系统优先看到“第二个”这一选择触发词，没有识别后面的“是什么意思”是词义提问。

改进方向：事件分类增加语义优先级：词义解释、否定和比较表达优先于候选选择；只有用户表达明确选择动作时才走 `resume`。

#### Bad Case 4：多城市请求没有拆分

```text
用户：查上海和无锡天气
期望：weather(上海) + weather(无锡)，两个独立任务
实际：只生成一个 weather 任务，query 为“查询上海和无锡天气”
样本：plan-085
```

原因：规划器按领域识别出 weather，但没有把同一领域中的多个实体拆成多个目标。

改进方向：规划校验不能只比较 domain 数量，还要检查实体数量；同领域多实体必须生成多个任务，并保留城市槽位。

#### Bad Case 5：依赖任务被降级成单任务

```text
用户：找餐厅后查看第一家详情
期望：local_search -> maps_place_detail
实际：仅生成一个 local_life 任务，没有依赖边和 bind_slots
样本：plan-094
```

同类样本：`plan-093`、`plan-095`、`plan-096`、`plan-098`、`plan-100`。

原因：规划失败后回退到了单任务意图识别，回退结果没有阻断执行，也没有明确标记“计划不完整”。

改进方向：多任务规划失败不能静默降级为单任务；应重新规划、请求澄清或返回不可执行状态。涉及前置结果的任务必须同时检查 `depends_on` 和 `bind_slots`。

#### Bad Case 6：恢复任务出现 409 Conflict

```text
用户补充澄清信息后恢复任务
实际：POST /api/tasks/{task_id}/resume 返回 409 Conflict
样本：clarified_completion-61、63、64、65、67、68 等
```

可能原因：恢复请求到达时任务已经被另一条执行路径推进、同一个 interrupt 被重复提交，或客户端拿到的是旧的 interrupt 快照。

处理方向：恢复接口增加 `interrupt_id + checkpoint_version` 条件校验；同一恢复请求使用幂等键；返回 409 时读取最新任务状态，区分“已经恢复成功”和“真正冲突”，不能盲目重试。

### B. 测试集标注 Bad Case

以下样本不能直接作为模型错误计入产品准确率，需要先修正测试集：

1. **日期标注与用户话术不一致**：多个样本用户只说“杭州会下雨吗”，但期望标成 `$tomorrow`；系统按当前日期执行后被判错。
2. **地点精度不一致**：用户说“会展中心”，期望却是“国家会展中心”；应定义别名归一化规则，不能直接字符串严格比较。
3. **默认位置口径冲突**：系统配置了无锡东南大学默认位置，但部分“附近饭店”“导航到西湖”样本仍要求必须澄清起点或锚点。当前策略固定为默认参考点，不追问起点；显式用户位置优先。
4. **事件序号标注错误**：`event-044` 的“去无锡校区”标成第一个候选；`event-051` 的“先选第一个”标成第二个候选。
5. **依赖任务用户策略不完整**：部分复合端到端样本没有提供后续 `title`、`destination`、`keyword` 等澄清答案，却要求系统完成全部任务。

## 六、结论与下一步

1. 原有 30 条基线和真实 MCP 30 条基线的通过结果仅为当时历史记录，不等同于当前统一定位策略下的评测。
2. 新增集暴露了真实长尾问题：取消目标映射、复合事件分类、多城市拆分、依赖规划、结果绑定和恢复竞态。
3. 当前新增集不能直接用端到端 46.7% 作为产品完成率，因为其中包含标注和用户策略不一致样本；此结论仍然成立，并进一步确认默认位置策略需统一为不追问起点。
4. 下一轮应先修正测试集 Gold：相对日期、默认位置、地点别名和复合任务目标；移除与产品策略冲突的 origin/anchor 澄清标签，修正后冻结数据集，再重新跑一次完整评测。
5. 代码层优先排查 409 恢复冲突、多城市同域拆分、依赖规划失败静默回退，以及事件分类中的取消和词义提问优先级。
